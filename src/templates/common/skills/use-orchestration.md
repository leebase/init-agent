# Skill: Use Agent-Orch And Auto-Orch

> Load this skill when you need to run a task through governed execution,
> convert a sprint plan into a playbook, launch or monitor a governed workflow,
> or decide between Agent-Orch and Auto-Orch.

---

## The Two Systems

| System | What it governs | Typical use |
|--------|-----------------|-------------|
| **Agent-Orch** | A playbook: ordered steps, validators, evidence, retry/halt | One delivery slice, feature, fix, sprint task, or PR-shaped workflow |
| **Auto-Orch** | A mission: envision, backlog, select, author, execute, evaluate, update | Ongoing autonomous loops, cron, mission memory, and learnings |

How they connect: Auto-Orch's Execute stage launches Agent-Orch through the
real CLI boundary. Do not replace that seam with ad hoc scripts or mock-only
proof.

---

## Decision Tree

Use **Agent-Orch** when the human names:
- a sprint item
- acceptance criteria
- one feature or fix
- a one-off governed delivery

Use **Auto-Orch** when the human names:
- a mission
- cron or scheduled operation
- backlog-driven autonomous work
- learnings or repeated cycles

When in doubt on an unfamiliar repo, start with Agent-Orch for one bounded
delivery slice. Move to Auto-Orch only when there is a durable mission and a
reason for repeated autonomous cycles.

---

## Agent-Orch Playbook Path

1. Read the target project's `AGENTS.md`, `context.md`, `WHERE_AM_I.md`, and
   `sprint-plan.md`.
2. Generate or adapt a playbook from an existing template instead of inventing
   a skeleton.
3. Map acceptance criteria into structural validation rules, not prose wishes.
4. Keep user-visible smoke gates and review gates on code-producing work.
5. Lint or preflight the playbook before launch.
6. Stop for human approval of the gates when the workflow can spend money,
   modify important files, deploy, or run unattended.
7. Launch through the real CLI and relay the trusted launch facts exactly.
8. On failure, inspect the dashboard/artifacts and verify evidence before
   retrying or resuming.

---

## Auto-Orch Mission Path

1. Create or inspect the mission directory.
2. Confirm `workspace` and `runs_dir` are absolute paths, with `runs_dir`
   outside the worker-writable workspace when possible.
3. Configure stage routing for Envision, Score, and Author through explicit
   CLI worker commands.
4. Fire one smoke cycle before installing cron or leaving it unattended.
5. Inspect `cycle-reports/`, `review-inbox.md`, `backlog.md`, and `state.md`.
6. Treat Author output as untrusted until the launched Agent-Orch run and its
   evidence pass.

Auto-Orch does not need a hand-written playbook every cycle. Author produces
the playbook; Agent-Orch governs the run.

## Sprint Plan To Playbook Mapping

| Sprint/task source | Playbook destination |
|--------------------|----------------------|
| Sprint goal or story title | Playbook name and contract step mission |
| Acceptance criteria | Step missions and structural validation rules |
| Tests must pass | Real test command with collected-output checks |
| Required docs section | Markdown heading/content validation |
| Required JSON output | JSON schema validation |
| Files that must not drift | Hash pins or explicit diff checks |
| Code review / QA | Review verdict gate |
| User-visible behavior | Smoke step with a real entry point |
| Human sign-off | Human approval step for one-off workflows only |

## Cross-Project Checklist

- [ ] Target repo is onboarded or already has the expected playbook/run layout
- [ ] Playbook or mission config is linted/preflighted
- [ ] Smoke and review gates exist for code-producing work
- [ ] Workspace and runs directory are explicit
- [ ] Launch facts come from trusted CLI output or a launch report, not worker prose
- [ ] Subprocess seams are covered by at least one real-boundary test or smoke
- [ ] Failed runs are inspected through artifacts before retry

---

## Anti-Patterns

| Do not | Do instead |
|--------|------------|
| Write playbooks from scratch when templates exist | Start from a known template and specialize |
| Use `file_exists` as the only gate | Validate content, schema, command output, or hashes |
| Launch without lint/preflight | Fix findings first, then launch |
| Summarize trusted launch output loosely | Relay exact run id, paths, and report facts |
| Treat worker narration as proof | Trust validators, artifacts, exit codes, and evidence |
| Mock the subprocess seam as the only proof | Run the real command boundary with fixtures |
