# Skill: Delegate Implementation To A Worker Harness

> Load this skill when a planning-capable session is about to implement a
> well-specified slice and a cheaper or separate worker harness should do the
> typing.

---

## The Split

The session doing planning, contracts, and review is the scarce resource.
Implementation of a well-specified slice is not, but delegation is safe only
when the spec is self-contained.

- **Planner**: rehydrate, decide, write contracts or plans, write task specs,
  review every diff, run final verification, update durable docs, and commit
  when allowed.
- **Worker**: implement exactly one spec with a narrow diff, focused tests, and
  an honest report back.

Spec quality substitutes for worker context. If the worker needs the chat
history to understand the task, the task is not ready to delegate.

---

## When To Delegate

Delegate:
- test authorship from a written contract
- mechanical implementation of contracted behavior
- broad but shallow edits such as renames or format bumps
- fixture writing

Do not delegate:
- contract decisions
- anything touching halt, approval, evidence, auth, or data-loss semantics
  without a written contract
- review judgment
- session-memory updates such as `context.md`, `WHERE_AM_I.md`, or final
  result documentation
- commits and pushes, unless the human explicitly told the worker to do them

---

## Task Spec Format

Every spec must stand alone. Include:

1. **Objective** — one paragraph, the contracted behavior in plain words.
2. **Files to touch** — explicit paths; anything else is out of bounds.
3. **Behavior details** — exact field names, thresholds, message shapes, and
   references to contract docs.
4. **Tests** — which tests to add or update, and what each must prove.
5. **Verification** — exact focused commands the worker should run.
6. **Boundaries** — what not to do: unrelated cleanup, new dependencies,
   doc churn, commits, or machine-managed files unless explicitly scoped.

---

## After The Worker Returns

The worker's report is untrusted prose. The planner must:

1. Read the full diff, every hunk.
2. Re-run the focused tests and formatters.
3. Check for boundary violations.
4. Run the relevant end-to-end or real-boundary smoke when the work touches a
   subprocess seam.
5. Only then fold the change into the development loop.

A worker never marks its own work done. Verification evidence comes from
commands the planner runs, not from the worker's summary.
